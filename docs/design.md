# 多节点复制系统设计

本文描述本仓库中的实现与迁移期间观察到的瓶颈，不等同于“当前线上已部署配置”。实际运行版本、参数和阶段必须以运行控制目录的最新部署记录及进程身份为准。代码归档不会自动启动或改变复制任务。

## 目标与边界

目标是在源目录持续可读、可能发生变化的条件下，将大量文件从全闪共享存储复制到混闪共享存储，同时支持跨节点扩展、失败恢复、目标冲突保护和可审计的完成证据。系统不删除源数据，也不把一次扫描解释为某个时间点的一致快照。最终一致性依赖后续轮次、文件校验及元数据收尾。

迁移范围按优先级分为 `home/hcr`、`repos/cosmos-framework-pwm`、其余 `eai_pwm` 和后继的 `/share/project`。前三项在 `eai_pwm` 范围内去重；第四项精确排除顶层 `eai_pwm`，使用独立控制目录与索引。第四项组件存在，不表示生产协调器已经完成交接或该阶段已启动。

## 数据流与职责

```text
共享源目录 ── 并行扫描 ── 目标存在性预检 ── 有界批次队列
                                  │
                                  ▼
                 主节点 HTTP broker + 本机 SQLite/WAL 唯一租约
                                  │
                         primary / supplement
                          多节点复制工作进程
                                  │
               临时文件校验、发布 → 持久逐文件回执
                                  │
                 历史索引恢复 / 后续轮次 / 元数据收尾

          metrics、inventory、progress、performance watch：旁路观测
```

- 扫描器按范围遍历目录并生成有限大小的文件批次。并行目录扫描与有界队列提高任务供给，同时限制内存和在途元数据操作。
- 目标预检只决定是否值得提交“缺失目标”的复制任务，不是复制成功证明。分布式 probe 可在多个执行节点做只读检查；响应须通过认证和协议/条目身份检查，失败会尝试其他端点，最终回退本地检查，不把网络错误视为目标存在或缺失。其当前代码范围限于原优先级 3。
- broker 以主节点本机 SQLite/WAL 作为跨节点任务分配权威；同一 owner 的重试取得原租约，完成回执按租约核对。不能用 NFS 上的 `rename`、`O_EXCL` 或本机 `flock` 代替跨节点唯一分配。并行 broker 将独立文件系统工作与短数据库临界区分离，同时保留 owner 锁与数据库约束。
- worker 按批次读取源文件、计算 SHA-256、写入目标临时文件并复读校验，检查源身份未变化并 `fsync` 后发布。已有目标按内容或符合当前源/目标身份的历史证明核验；不属于本任务的不同内容应报告冲突，不盲目覆盖。
- 回执、状态快照和索引放在任务控制目录。可变 JSON 由 `migration_io` 的不可变快照接口读写；canonical JSON 可能是旧版本。运行控制数据、认证令牌和本机 broker 数据库不随源码进入 Git。

## 恢复、去重与“总进度”

恢复单位是**文件的完整成功证据**，不是文件内部字节偏移。已持久化且身份仍匹配的回执可复用；没有完整证明的文件可能整文件重拷。`resume_from` 祖先链上的回执构成历史证据，不能因旧节点 `/tmp` 或进程消失而忽略。索引构建按相对路径合并，须校验文件类型、大小、摘要与源/目标身份；单纯的 broker replay 标记不构成独立写入证明。

“历史唯一成功量”和“本次恢复队列确认量”可能高度重叠，不能直接相加。精确累计量必须按范围和相对路径合并历史索引与本轮结果，并区分已核验、实际新写入及仍待检查。清单未完整扫描时，总规模只有下限，完成比例和 ETA 均应显示未知。物理线程活跃率、逻辑传输 GiB/s、真实新增唯一量是不同指标；逻辑字节尤其不能直接当作底层盘带宽。

## 性能问题与处理

### 2026-10-22：交错供给与训练解耦

源目录遍历目前仍在 master 的一个 Python 进程内使用 128 个目录线程；目标存在性检查及旧候选源身份刷新分布到 12 个节点。不能把“12 节点复制/检查”描述成“12 节点目录遍历”。主线程独占路径预约、任务编号和 SQLite，8 个发布线程只负责独立任务文件的发布。

旧优先供给策略存在另一种饥饿：约 550 万旧孤儿候选必须等待新目录遍历全部结束才进入检查。`migration_interleaved_target_filter.py` 将旧候选（大文件优先）与新扫描交错送入同一有界检查池，复用唯一预约者；没有新增第二个不协调的 producer。`migration_prepared_resume.py` 在旧 producer 运行期间准备完整路径/硬链缓存、清单前缀及本地候选 spool，交接只加载缓存并合并尾部和任务增量。缓存采用摘要、路径/权限绑定及禁止解析全局对象的反序列化器；历史大集合冻结出循环 GC，新增对象仍正常回收。实际 3,216 万路径缓存加载约 30 秒，不包括清单摘要预检和交接尾部合并。

停机恢复必须识别已经交回 broker、但文件结果为 `paused` 或 `cancelled` 的任务，按持久回执单独重试；不能因为任务状态为 `done` 就丢弃未完成文件。成功路径与仍有租约的路径不重新派发。已有目标的存在性检查仍不是内容核验，正式轮次和 SHA 校验保持不变。

本次用户明确要求训练与复制解耦，运行配置设置 `training_watchdog_enabled=false`。`migration_watchdog.py` 启动和循环均遵守该开关；恢复脚本只归档已核对的训练退出 STOP，不清除未知停止原因，不操作训练进程。复制自己的 STOP、唯一租约和文件安全检查仍然有效。

只读 probe 支持每节点最多 128 路，生产滚动调整到 64 路；可选 `--stop-cache-seconds 0.1` 将同进程重复 STOP 查询合并成最多每 100 ms 一次。缓存一旦观察到 STOP 即保持停止；它不缓存目标存在性，也不降低内容校验。滚动更新只替换身份核实的 probe，worker、broker 和 producer 不重启。

吞吐不能脱离文件粒度解释。一次前后各 300 批次抽样，平均文件大小从约 233 MiB 降到 1.7 MiB；同样的 10 GB/s 需要约百倍文件处理率。裸 `cp` 不会解决发现/派发供给不足，且不能直接替代当前摘要、回执及源变化检查。验收应比较持续窗口的写入速度、完成速度、各阶段供给量和端点新增错误率，不能用瞬时峰值或线程配置总数宣称达标。

| 观察到的问题 | 原因与处理 | 验证/剩余边界 |
| --- | --- | --- |
| 复制线程活跃数远低于配置总数 | 通常是上游恢复队列、目录扫描或目标检查供给不足。并行扫描、批次生成和分布式只读目标 probe 用来提高任务供给；应先看待处理队列、在途检查及检查错误率，再考虑增加 worker。 | 增大复制线程数本身不能解决空队列，且可能增加共享存储负载。 |
| 单点目标检查拖慢恢复队列 | 大量 `stat`/存在性请求集中在主节点，慢或失败端点造成重试。probe 分散到多个节点、设置单节点并发上限与总体在途上限，并提供本地回退。 | 2026-10-22 的一次监控快照中，目标检查端点错误率约 79.8%，同时复制线程仅 103/1,536 活跃；这是诊断例子，不表示该端点现已修复。应持续按端点监测错误率和延迟，必要时先定位网络/服务原因。 |
| broker 同步处理共享存储操作造成排队 | 分配的唯一性需要串行短事务，但慢 NFS I/O 不应占住整个处理路径。并行 broker 采用 owner 锁、SQLite 约束及有限文件系统并发。 | 观察 claim 延迟、积压、WAL 状态和重试幂等；不能牺牲唯一租约来换吞吐。 |
| 每个 worker 高频读取共享状态产生元数据负载 | 进程内状态缓存仅拦截指定状态路径，由刷新线程读取，消费者得到独立副本。 | 刷新失败或缓存过期时拒绝继续领新任务；STOP 仍直接检查，不允许无限使用旧状态。 |
| 共享盘长尾导致 `state cache is stale` 反复重试 | 3 秒的缓存有效期会被状态读取长尾耗尽；一次约 61 秒的采样中，12 个进程新增 1,666 次相关重试。在线逐进程将有效期显式调整为 30 秒，仍保持刷新失败即拒绝新任务和直接 STOP 检查。 | 这是减少状态读取抖动的措施，不是放宽数据校验；30 秒仍可能遇到更长尾延迟，需持续观察新增重试。 |
| 扫描线程多但任务队列仍空 | 运行侧采样发现 producer 约 385 个线程却只用约 1 个 CPU 核，主线程仍串行执行任务批次的 SQLite 处理及共享盘发布，probe 服务大多空闲。 | 先定位扫描、预检、发布各段延迟；不能仅据线程数判断 CPU/GIL 瓶颈，也不能靠增加复制线程解决供给不足。 |
| 生产主线程同步发布每一批任务 | 新恢复队列入口采用有界并行发布池。路径预约、任务编号和索引查询仍由主线程完成，后台只发布唯一的新任务文件；成功后由主线程收集并更新统计。 | 2026-10-22 的只读点查平均约 0.007 ms，不能据源码把 SQLite 认定为主瓶颈。独立任务文件发布测试有并行收益，但不等于端到端复制提速，仍须对比上线后的供给、队列和复制速率。 |
| 替换进程漏继承 NOFILE，扫描途中因 EMFILE 退出 | SSH 启动的 soft limit 为 1,024，而并行目录读者、目录迭代器和元数据连接会同时持有更多句柄。生产进程现在启动时自行提升并核实至少 65,536，hard limit 不足则在任何协调器副作用前拒绝启动。 | 启动后检查实际 `/proc/PID/limits`；回归测试以真实低限额子进程同时打开 1,536 个句柄。验收还须让实际扫描 FD 超过旧阈值并持续发布、复制，不能只验进程启动或 mock 通过。 |
| 恢复时历史回执/索引重建耗时 | 沿祖先链读取大量小回执并写入去重索引，易受共享存储延迟影响。采用有界并行读取、内存 TEMP 表与确定性合并；缺失目标优先的复制队列可与索引恢复重叠。 | 恢复重建完成前不能把区间估算冒充精确累计，也不能省略交接隔离与回执校验。 |
| 重放旧清单重新检查数百万个已有目标，阻塞新供给 | 原恢复器在 seed 旧清单时就逐项提交 orphan HTTP 预检；实测约 540 万项、700 项/秒，远超纯 JSON 解析的耗时。优先供给版本将这些记录完整保存到本地临时 spool，先完成清单 seed 和新扫描供给，再核对旧 orphan。 | 不删除或丢弃旧记录，全部完成前不标记扫描结束。阶段/seeded/deferred/consumed 均可观测；不能把进程存活或新 manifest 出现当作供给已经恢复。 |
| 更多并发可能放大而非消除瓶颈 | 线程数必须按物理节点合并 primary 与 supplement，观察真实活跃线程、任务队列、源/目标延迟及训练负载。 | 小规模 canary、连续有效采样与回退判据先于全量调整；监控程序本身不自动调并发。 |

## 不打断在途文件的在线更新

`rollout_cache_cluster.py` 顺序调用 `rollout_cache_age.py` 的 protocol 2，每次仅更新一台机器的一个复制进程。先由 broker 暂缓该节点领取新任务，再等待目标进程租约归零、两次新心跳均空闲，核对 PID、启动时刻、完整参数及没有打开的源/目标数据文件，才终止空闲进程并启动替代进程。其他节点和所有在途文件继续复制；复制引擎、线程数、I/O 预算以及累计计数保持不变。已达目标配置的进程也必须验证实际身份与健康状态，不能仅凭历史部署记录跳过。

控制目录的共享盘传播可能晚于 broker 实际状态，因此只允许有界的只读重查，不放宽安全条件。控制请求超时不代表操作未生效；结果不明时停止推进，保留现场并核对实际 drain、进程身份和持久回执，不能盲目重发替换。每次发布使用新 helper 目录，保留逐进程和集群级记录。验收同时检查全部实际启动参数、计数不回退、无残留 drain、STOP 未触发，以及 producer、broker、训练进程身份未改变；随后采样新增重试和吞吐，不能把不同文件大小下的速度变化直接归因于更新。

生产进程交接与空闲 worker 更新不同：当前扫描器没有可持久恢复的目录游标，重放巨大历史清单可能造成数分钟的新任务供给空窗。不能用输出 manifest 的字节位置冒充扫描前沿，也不能启动第二个 producer 用不同 ID 号段绕过交接——进程内路径去重无法阻止两边同时复制同一文件。新的并行发布入口保留单一 producer；发布失败时记录 `producer_paused` 而非会令空闲 worker 永久退出的 `failed`。已接受的发布不取消、预留编号不回退，扫描完成和发布池并发调整均以全部已接受任务排空为边界。

## 运行与验收原则

只读监控入口：`python3 /share-mixed/project/.hcr-copy-monitor/progress.py --watch`。它显示运行任务的状态，不应由本仓库文件存在与否推断部署成功。判断当前入口需同时核对最新部署记录、PID、启动时间和完整 argv；运行脚本中不少是绑定旧控制目录的一次性运维记录，不可盲目重跑。

验收要覆盖全部四项范围、最终轮次 summary/finalize、未解决 issues、硬链接和目录元数据、后台队列/进程，以及累计唯一索引。`complete_with_changes` 需要人工审阅差异。任何 `0` 或“完成”的观测值都必须有可读取的实际证据；读取失败应显示未知或错误。
