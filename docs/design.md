# 多节点复制系统设计

本文描述本仓库中的实现与迁移期间观察到的瓶颈，不等同于“当前线上已部署配置”。实际运行版本、参数和阶段必须以运行控制目录的最新部署记录及进程身份为准。代码归档不会自动启动或改变复制任务。

## 目标与边界

目标是在源目录持续可读、可能发生变化的条件下，将大量文件从全闪共享存储复制到混闪共享存储，同时支持跨节点扩展、失败恢复、目标冲突保护和可审计的完成证据。系统不删除源数据，也不把一次扫描解释为某个时间点的一致快照。最终一致性依赖后续轮次、文件校验及元数据收尾。

迁移范围按优先级分为 `home/hcr`、`repos/cosmos-framework-pwm`、其余 `eai_pwm` 和后继的 `/share/project`。前三项在 `eai_pwm` 范围内去重；第四项精确排除顶层 `eai_pwm`，使用独立控制目录与索引。第四项组件存在，不表示生产协调器已经完成交接或该阶段已启动。

## 数据流与职责

```text
共享源目录 ── 并行扫描 ── 目标存在性预检 ── 有界批次队列
                                  │
                                  ▼
                 主节点 HTTP broker + 本机 SQLite/WAL 唯一租约
                                  │
                         primary / supplement
                          多节点复制工作进程
                                  │
               临时文件校验、发布 → 持久逐文件回执
                                  │
                 历史索引恢复 / 后续轮次 / 元数据收尾

          metrics、inventory、progress、performance watch：旁路观测
```

- 扫描器按范围遍历目录并生成有限大小的文件批次。并行目录扫描与有界队列提高任务供给，同时限制内存和在途元数据操作。
- 目标预检只决定是否值得提交“缺失目标”的复制任务，不是复制成功证明。分布式 probe 可在多个执行节点做只读检查；响应须通过认证和协议/条目身份检查，失败会尝试其他端点，最终回退本地检查，不把网络错误视为目标存在或缺失。其当前代码范围限于原优先级 3。
- broker 以主节点本机 SQLite/WAL 作为跨节点任务分配权威；同一 owner 的重试取得原租约，完成回执按租约核对。不能用 NFS 上的 `rename`、`O_EXCL` 或本机 `flock` 代替跨节点唯一分配。并行 broker 将独立文件系统工作与短数据库临界区分离，同时保留 owner 锁与数据库约束。
- worker 按批次读取源文件、计算 SHA-256、写入目标临时文件并复读校验，检查源身份未变化并 `fsync` 后发布。已有目标按内容或符合当前源/目标身份的历史证明核验；不属于本任务的不同内容应报告冲突，不盲目覆盖。
- 回执、状态快照和索引放在任务控制目录。可变 JSON 由 `migration_io` 的不可变快照接口读写；canonical JSON 可能是旧版本。运行控制数据、认证令牌和本机 broker 数据库不随源码进入 Git。

## 恢复、去重与“总进度”

恢复单位是**文件的完整成功证据**，不是文件内部字节偏移。已持久化且身份仍匹配的回执可复用；没有完整证明的文件可能整文件重拷。`resume_from` 祖先链上的回执构成历史证据，不能因旧节点 `/tmp` 或进程消失而忽略。索引构建按相对路径合并，须校验文件类型、大小、摘要与源/目标身份；单纯的 broker replay 标记不构成独立写入证明。

“历史唯一成功量”和“本次恢复队列确认量”可能高度重叠，不能直接相加。精确累计量必须按范围和相对路径合并历史索引与本轮结果，并区分已核验、实际新写入及仍待检查。清单未完整扫描时，总规模只有下限，完成比例和 ETA 均应显示未知。物理线程活跃率、逻辑传输 GiB/s、真实新增唯一量是不同指标；逻辑字节尤其不能直接当作底层盘带宽。

## 性能问题与处理

### 2026-10-22：交错供给与训练解耦

早期源目录遍历在 master 的一个 Python 进程内使用 128 个目录线程；目标存在性检查及旧候选源身份刷新分布到 12 个节点。最新恢复供给改为 master 上 8 个独立目录读取进程和 8 个检查客户端进程，12 个目标检查节点保持运行。主线程独占路径预约、任务编号和 SQLite，8 个发布线程只负责独立任务文件的发布。

目录读取使用 `spawn`，通过有界双向 Pipe 返回最多 256 项的目录页面。主进程利用唯一历史路径集合选择未知叶子，子进程在持有且身份已核实的目录 FD 上并发读取这些叶子的元数据；因此不用向每个进程复制 3,300 万路径，也不会为了已知叶子重复做 `stat`。硬链归属、清单和任务回调均留在主进程。目录队列满时使用安全的本地深度遍历；取消或出错时回收子进程。

检查客户端以每批最多 64 项的有界 IPC 传给独立进程，再调用认证的 `/probe-batch`。检查服务复用受同一文件系统并发槽限制的线程池，逐项返回结果和错误；批次协议或单项校验失败时沿用原来的跨节点重试和本地只读回退。检查进程只能返回元数据结果，不写任务、不分配编号、不打开迁移索引。生产配置为 `source_scan_processes=8`、`source_scan_threads_per_process=16`、`metadata_client_processes=8`、`metadata_threads_per_process=64`、`metadata_client_batch_size=64`；正式轮次默认实现保持不变。

这次改动前约 1.38 核的采样中，主线程本身只占约 0.12 核，大量检查 future 已完成却等待主循环收割；CPU 使用率不能单独证明 CPU 已饱和。改动后的生产采样检查率约 1.35 万项/秒，较之前约 1,563 项/秒提高约 8.6 倍；吞吐与 CPU 数均应以真实采样验收。文件粒度变化时还应同时比较文件完成率，不能把小文件阶段的逻辑字节速率与之前大文件阶段直接等同。

### 供给扩容后：派发和回执的目录热点

供给提高后出现大量“SQLite 已 leased、worker 却尚未 active”的线程。采样中约 1,300 个线程等待 broker 返回，64 个共享盘操作槽位全部被目录操作占住；问题发生在租约已经持久化之后，不能归因于没有任务或 SQLite 无法分配。

`migration_broker_sharded.py` 将新租约的运行标记放到 `running/<task_id % 64>/`，原数据库中保存的旧绝对路径继续有效。还需要同时满足两个条件：预建 running/done 的父目录后，热路径用 `write_json(..., ensure_parent=False)` 跳过冗余的 `mkdir(EEXIST)`；ready 缓存按 64 个 pending 分片轮询交错填充。如果仍逐片派完所有任务，运行标记和回执也会集中到同一片，采样曾出现 1,201 个租约中的 1,193 个落在三个目录。只改文件路径而不改派发顺序并不能分散并发。

协调器的 `queued_count` 和只读 census 同时支持旧平铺和新分片，空目录不算运行任务，目录打开拒绝符号链接，避免误判阶段排空。broker 交接保留原本机 SQLite/WAL、端口、鉴权、drain 状态和逐条旧 lease；worker 和在途复制保持运行。

最终约 32 秒生产采样：实际复制约 8,564 文件/秒，较早期约 692 文件/秒提高 12.4 倍；活跃线程约 1,500/1,536，其中等待回执约 10 个；1,531 个租约均匀分布于全部 64 片（每片 22–26 个）。broker 的线程从上千降至个位数至几十，新增重试为零。该样本文件平均约 40 KB，写入约 0.346 GB/s，是小文件处理率的验证，不是持续 10 GB/s 的证明。

旧优先供给策略存在另一种饥饿：约 550 万旧孤儿候选必须等待新目录遍历全部结束才进入检查。`migration_interleaved_target_filter.py` 将旧候选（大文件优先）与新扫描交错送入同一有界检查池，复用唯一预约者；没有新增第二个不协调的 producer。`migration_prepared_resume.py` 在旧 producer 运行期间准备完整路径/硬链缓存、清单前缀及本地候选 spool，交接只加载缓存并合并尾部和任务增量。缓存采用摘要、路径/权限绑定及禁止解析全局对象的反序列化器；历史大集合冻结出循环 GC，新增对象仍正常回收。实际 3,216 万路径缓存加载约 30 秒，不包括清单摘要预检和交接尾部合并。

停机恢复必须识别已经交回 broker、但文件结果为 `paused` 或 `cancelled` 的任务，按持久回执单独重试；不能因为任务状态为 `done` 就丢弃未完成文件。成功路径与仍有租约的路径不重新派发。已有目标的存在性检查仍不是内容核验，正式轮次和 SHA 校验保持不变。

本次用户明确要求训练与复制解耦，运行配置设置 `training_watchdog_enabled=false`。`migration_watchdog.py` 启动和循环均遵守该开关；恢复脚本只归档已核对的训练退出 STOP，不清除未知停止原因，不操作训练进程。复制自己的 STOP、唯一租约和文件安全检查仍然有效。

只读 probe 支持每节点最多 128 路，生产滚动调整到 64 路；可选 `--stop-cache-seconds 0.1` 将同进程重复 STOP 查询合并成最多每 100 ms 一次。缓存一旦观察到 STOP 即保持停止；它不缓存目标存在性，也不降低内容校验。滚动更新只替换身份核实的 probe，worker、broker 和 producer 不重启。

吞吐不能脱离文件粒度解释。一次前后各 300 批次抽样，平均文件大小从约 233 MiB 降到 1.7 MiB；同样的 10 GB/s 需要约百倍文件处理率。裸 `cp` 不会解决发现/派发供给不足，且不能直接替代当前摘要、回执及源变化检查。验收应比较持续窗口的写入速度、完成速度、各阶段供给量和端点新增错误率，不能用瞬时峰值或线程配置总数宣称达标。

### 2026-10-23：小文件目录元数据与重复预检

小文件阶段的 21 秒生产采样只有约 2,130 文件/秒、38.4 MB/s，活跃 616/1,536；文件平均约 18 KB。目标检查与任务供给约 2,200 项/秒，发布池仅积压 1/64，broker 没有拥塞。producer 主进程仅约 0.15 核，八个扫描进程约 0.21 核，八个检查客户端约 0.08 核：源扫描被等待目标预检的主循环反压，并非缺少扫描线程。

逐文件目标检查平均约 86–132 ms。复制进程的目录遍历对已有祖先反复 `mkdir(EEXIST)`，同时，检查服务从 `/` 逐组件打开目录。前者已改为安全 open-first、仅缺失时创建；后者在支持的 Linux 内核使用 `openat2(NO_SYMLINKS | NO_MAGICLINKS)` 一次打开完整父目录，不支持时退回同样严格的逐组件 `O_NOFOLLOW` 遍历。没有缓存陈旧目录 FD，也没有放宽符号链接、摘要、源身份、冲突或 fsync 检查。容器不允许读取内核栈/syscall，目录锁热点判断结合了源码与 wchan，不能声称已拿到精确 syscall 栈。

父目录打开微基准约快 2.4–3.5 倍，不等于复制端到端提升：24 个复制进程、12 个检查服务滚动更新后的初始窗口仍只有约 2,353 文件/秒、42.6 MB/s；目标检查约 2,771 项/秒，平均约 107 ms，缺失目标查询仍形成供给瓶颈。必须继续以实际复制采样验收，不能把更新完成或微基准当作提速成功。

`migration_small_probe_delegate.py` 最初使用显式静态策略控制：只有完整源身份的新扫描普通小文件（最初上限为 64 KiB），所在父目录已经观察到至少 16 个真实缺失且从未命中已有目标，才可把重复的存在性预检交给复制 worker；每 64 项仍重新预检，观察到已有目标立即永久禁用该目录。目录状态最多 4,096 项，已有目标的禁用记录不淘汰；无法继续有界保存时退回原预检。历史候选的源刷新、已有验证记录、符号链接和超过策略上限的文件仍走完整预检。后续策略扩展及热重载见下一节。

此策略不构成“目标不存在”的证明。旧 wire 字段 `missing=true` 仅表示向 worker 提交待复制/核验候选，额外的 `precheck_delegated` 和独立 `delegated_small_files` 计数明确其未预检；健康信息把真实缺失/已存在采样分开。worker 的 `_existing_file`、SHA、冲突拒绝和成功回执完全不变，已有目标依旧需要核验而非重写。生产是否启用以不可变 bundle 的 `probe-policy.json`、实际进程身份与健康信息为准。

复制侧也通过 `worker-directory-policy.json` 显式启用相同的安全单次父目录打开；默认仍为保守逐组件路径，缺目录时只对 ENOENT 回退创建，其他错误直接拒绝。一次同节点约 20 秒对照中，新进程约 467 文件/秒，旧进程约 394 文件/秒，平均文件大小接近且无新增错误。这只是单进程短窗口，并非对全局相同比例收益的保证。

worker 更新复用 protocol-2 的 drain、租约为零、两次空闲心跳、无数据 FD 与精确进程身份检查；显式 transition manifest 只允许完整 SHA 绑定的 `migration_worker.py` 变化，另外五个引擎文件必须相同，新 wrapper、native helper 和静态策略也全部绑定源文件摘要。64 文件批次的长尾可超过 30 秒，因此最多继续三次同一操作下的只读空闲观察，绝不重复结果不明的 replace。`rollout_native_parallel.py` 最多同时处理三个物理节点，同节点两条 lane 仍顺序；整个 pass 只持有一个主控交接锁，所有 drain/release 的完整读改写 RPC 串行执行，防止丢失其他节点的 drain。首次不确定结果停止新节点/新 lane，在途交接按原安全流程收尾。

供给恢复后还观察到：约 2,830 个 pending 批次已经存在，但 broker 在 ready 缓存耗尽时持缓存锁顺序枚举全部 64 个目录，实际目录清点耗时约 3.3 秒，造成周期性 claim 等待。最终改为至多 8 路只读分片枚举，每路仍持原全局文件系统槽位，全部成功后才按原 round-robin 顺序填入缓存；任一读取错误直接传播，不当作空队列。此次 broker 独立身份绑定交接保留同一本机 SQLite/WAL、1,504 个在途租约和全部 worker 身份；producer 未重启，历史清单未重放。

末次连续三个约 20 秒窗口：实际复制约 9,604、10,065、9,686 文件/秒，写入约 1.14、1.20、1.16 GiB/s，活跃 1,522、1,529、1,507/1,536；新增复制错误、冲突、源变化和 broker 重试均为零，drain 为空。全部 24 个 worker 的真实 PID、启动时刻、完整 argv、累计计数和预算均另行跨节点核验。相比初始约 2,130 文件/秒，处理率明显恢复；但当前文件平均约 128 KB，较初始约 18 KB 更大，不能把逻辑字节速度的全部倍数归因于优化，也未达到 10 GB/s。

### 2026-10-23 14 时：覆盖当前图片粒度，保持复制进程不变

后续现场基线的约 25 秒窗口为 6,060 文件/秒、0.721 GiB/s，平均文件 127,799 字节，活跃 670/1,536。待领队列只有几十个批次，发布池积压 0–5/64；增加发布线程没有依据。虽然配置写着 512 路目标检查，实际是 8 个同步 HTTP 批次客户端、每批至多 64 项，批次内的慢项及重复目标元数据检查会反压生产主循环。旧 64 KiB 策略只委托约 9% 的候选，其余文件进入复制 worker 前仍重复查询目标。

将候选大小上限有界扩展到 1 MiB，保留完整源身份、至少 16 次真实缺失、每 64 项复查、已有目标目录永久禁用和 4,096 目录内存界限。单端点对照中，平均每项预检计时从约 34 ms 降到 7 ms，委托候选比例约 72%；全局速度没有立刻明显改善，因此先验证端点机制，再逐个推广到其余十一端点。worker 仍检查实际目标并执行 SHA/冲突判断，不能把这些委托项计作已证实缺失或复制成功。

用户明确允许只读预检服务逐个切换，要求复制不停止。`deploy_probe_policy.py` 冻结前任十二个 probe 的完整 PID/启动时刻/argv，以及二十四个复制进程和主节点 producer、broker 的身份；沿用一次性、有摘要绑定的 probe 替换事务，每次只处理一个端点。替换前后检查受保护身份，遇到不确定结果立即停止，不重试替换。在生产负载导致元数据槽暂时全满时，只允许有界重试只读协议验证，不允许重试信号或启动。整个更新未 drain、重启复制进程，未交接 producer/broker、改队列编号或重放历史清单。

新 probe 后台每 5 秒读取可选 `BUNDLE/roles/probe-policy-runtime.json`，请求处理路径不读策略文件。运行态覆盖不属于平铺的不可变源码摘要清单；必须使用 `migration_io.write_json/read_json` 的快照约定。仅 `max_file_bytes` 可在 0–1 MiB 内热改，目录预算、采样门槛和复查间隔不能热改；坏配置/读取失败保留上一次有效策略，健康信息报告 `revision` 和 `reload_error`。策略变化保留暖目录和所有已有目标禁用记录。主节点 canary 已在同一 probe PID 下完成 64 KiB → 1 MiB 的生效验证，再向其余节点推广。

更新后连续三个约 20 秒窗口为 1.251、1.210、1.211 GiB/s，10,521、10,187、10,145 文件/秒，活跃 1,513、1,524、1,515/1,536；平均文件仍约 128 KB。三个窗口新增复制错误、冲突、源变化、暂停及 broker 重试均为零；全部二十四个复制进程的实际身份另行核对未变。不能据此宣称达到了 10 GB/s，或把这三个窗口当作包含后续停顿的长时间平均。

随后还抓到一次独立的生产端垃圾回收停顿：北京时间 14:15:33 至 14:16:30，状态发布间隔约 57.42 秒，`supply_metrics.gc_seconds` 增加 56.28 秒，目标候选提交数没有增加；队列耗空后所有复制线程短时空闲，但进程未退出，之后自动恢复。现有指标没有记录 GC generation，因此不将其表述为已证实的某一代回收。14:19:39 的监控为最近 1 分钟约 1.2 GiB/s、活跃 1,527/1,536；包含该停顿的最近 5 分钟约 1,017 MiB/s。该生产端没有 GC 热配置接口，当前更新没有注入或重启它；受控回收与相应热调能力仍是后续生产端发布的待解决项。

现场证据保存在任务控制目录的 `probe-policy-baseline-20261023T0614.json`、`probe-policy-canary-20261023T0617.json`、`probe-policy-final-20261023T0614.json`，以及新 bundle 的 `roles/cluster-rollout.json`、`roles/hot-reload-canary.json`、`roles/copy-identities-postflight.json`。文件名后缀是本次操作标签，实际时间以内部采样时间戳为准；这些运行数据与身份不纳入源码仓库。

### 稳态复制瓶颈与目标父目录 O_PATH 候选

不能把所有吞吐不足归因于 GC。后续约 25 秒稳定窗口已达到 1,522/1,536 活跃、约 1.30 GiB/s 和 10,952 文件/秒，待领任务约 1,579 批，回执等待仅 8 个线程；此前约 392 秒窗口累计 GC 仅占约 0.18%。另一次约 56 秒 GC 停顿仍会造成独立的供给空窗。这两类瓶颈必须分开计量，不能将短时回收停顿解释为持续七倍的吞吐差距。

当前平均文件约 128 KB，10 GB/s 需要约 7.8 万文件/秒，而不仅是提供足够的字节带宽。三个节点的只读 `/proc` 采样以 RPC 等待和 inode rwsem 等待为主；挂载级 NFS CREATE/LINK/REMOVE 平均约 10–20 ms，而客户端传输排队很短、未见重传。这些是挂载级统计，不是逐进程 syscall 跟踪，也不能据此宣称已证明服务器的硬性吞吐上限。普通 `cp` 同样需要创建文件和处理元数据；降低校验或持久化语义后得到的更高速度不能当作等价替代的证明。

严格保持 `openat2` 的 `NO_SYMLINKS|NO_MAGICLINKS`、`DIRECTORY|NOFOLLOW|CLOEXEC`，只把目标父目录的 `O_RDONLY` 改为 `O_PATH`，两个节点的只读交错微基准平均从约 4.46/5.82 ms 降到 0.19/0.14 ms。源目录差异很小，因此不改源目录，也不改需要读目录或应用目录元数据的 root FD。`O_PATH` FD 仅用于 `*at` 和 `fstat`；缺目录仍走原来的保守创建路径。这个结果只证明单个操作可优化，不证明复制吞吐有相同比例增益。

`destination-opath-checkpoint-v1` 发布范围只允许启动器、辅助代码和策略变化，六个数据引擎文件必须逐字节相等，SHA 校验、源身份检查、fsync、防覆盖发布均不变。新进程必须绑定本次 host/lane/operation 的空闲检查点；启动预检以及原 worker 在单实例 flock 内真正读取旧节点记录时均校验 `run_started`、累计字节/文件数和嵌套阶段计数。失败抛出独立的 `RuntimeError`，不允许被旧入口的 `except (OSError, ValueError): previous={}` 吞掉。验收还需检查新进程计数不低于交接基线，不能用监控侧 `max()` 掩盖源计数清零。

该候选必须先在一个节点的一条 lane 上排空后对照，保留同一控制目录、队列、租约权威和统计流；其他节点继续复制，producer/broker 不交接。`observe_worker_canary.py` 记录分 lane 的新增文件/字节、平均文件大小、GC 时间和身份，窗口内 PID 变化或计数回退直接拒绝比较。代码和 bundle 准备完成不代表已部署，只有真实交接记录和更新后的端到端采样才可作为推广依据。

## 不打断在途文件的在线更新

`rollout_cache_cluster.py` 顺序调用 `rollout_cache_age.py` 的 protocol 2，每次仅更新一台机器的一个复制进程。先由 broker 暂缓该节点领取新任务，再等待目标进程租约归零、两次新心跳均空闲，核对 PID、启动时刻、完整参数及没有打开的源/目标数据文件，才终止空闲进程并启动替代进程。其他节点和所有在途文件继续复制；复制引擎、线程数、I/O 预算以及累计计数保持不变。已达目标配置的进程也必须验证实际身份与健康状态，不能仅凭历史部署记录跳过。

控制目录的共享盘传播可能晚于 broker 实际状态，因此只允许有界的只读重查，不放宽安全条件。控制请求超时不代表操作未生效；结果不明时停止推进，保留现场并核对实际 drain、进程身份和持久回执，不能盲目重发替换。每次发布使用新 helper 目录，保留逐进程和集群级记录。验收同时检查全部实际启动参数、计数不回退、无残留 drain、STOP 未触发，以及 producer、broker、训练进程身份未改变；随后采样新增重试和吞吐，不能把不同文件大小下的速度变化直接归因于更新。

生产进程交接与空闲 worker 更新不同：当前扫描器没有可持久恢复的目录游标，重放巨大历史清单可能造成数分钟的新任务供给空窗。不能用输出 manifest 的字节位置冒充扫描前沿，也不能启动第二个 producer 用不同 ID 号段绕过交接——进程内路径去重无法阻止两边同时复制同一文件。新的并行发布入口保留单一 producer；发布失败时记录 `producer_paused` 而非会令空闲 worker 永久退出的 `failed`。已接受的发布不取消、预留编号不回退，扫描完成和发布池并发调整均以全部已接受任务排空为边界。

## 运行与验收原则

### 集群整体失效后的恢复边界

旧 1e56 集群失效后，c3559 新节点仍可读取共享清单和目标数据，但旧主节点 `/tmp` 下的租约 SQLite、恢复索引以及 primitive 路径缓存均不可用；约 94 GB 的活动清单仍在共享盘。不能把滚动换 PID 的计数继承机制误当作跨集群恢复，也不能照搬依赖旧数据库和 prepared pickle 的热交接入口。

新集群实测 12/12 SSH 可用，但 worker-9 的 `/share-mixed/project` 是 XFS，而其余十一台为目标 NFS；该节点没有目标数据树，必须从部署白名单和所有任务角色中排除。挂载校验失败不自动 mkdir 或写本地目录。用户授权按十一节点恢复后，`deploy_crash_cluster.py` 使用新控制目录、run_id、令牌和新主机身份；旧控制目录只增加 STOP 隔离标记，保留清单、队列和回执。隔离记录明确区分“用户报告旧集群失败＋心跳失效＋共享 STOP”与“独立验证平台删除”，不将前者虚报为后者。

只导入旧 warm stage 的 pending/running 候选，按原任务 ID 检查一致性，并以完整成功回执排除已完成条目，再按相对路径去重；不得将未知/失败当作成功。旧 owned 替换证明不作为 warm 复制的授权，候选目标存在时先过滤，缺失时刷新源身份后交给完整校验 worker。此次冻结导入为 190 个批次、12,160 个路径，这些是候选而非保证仍需传输的文件。

`migration_crash_resume.py` 复用新命名空间的 overlap bootstrap、唯一任务编号与有界并行发布，不调用依赖旧 `/tmp` 的 live-handover 构造器。八个源扫描进程与八个预检客户端进程并行工作，预检分布于允许的十一节点；历史回执通过独立子进程重建并合入新索引，严格枚举模式不把权限/目录读取错误解释为空。正式轮次和第四项计划仍保留，warm 队列不冒充正式轮次完成。新角色启动检查主机白名单和实际挂载，记录精确 PID/starttime/argv；生产端死后不盲目重启，训练 watchdog 显式禁用。

监控的 `recovery-baseline.json` 冻结旧任务已记录写入计数和存在性命中观察，且绑定新 control/run_id/resume_from。展示“含旧任务的已记录累计”与“本次恢复新增”两行，不能把历史与新核验次数相加冒充唯一文件数。速率仍由新运行的累计计数差值计算，不能把基线接入时的常数跳变算作吞吐。准备成功、启动控制器存活或 SSH 返回成功均不是恢复验收；须继续核对 22 个复制进程、真实心跳、回执、错误和端到端新增量。

只读监控入口：`python3 /share-mixed/project/.hcr-copy-monitor/progress.py --watch`。它显示运行任务的状态，不应由本仓库文件存在与否推断部署成功。判断当前入口需同时核对最新部署记录、PID、启动时间和完整 argv；运行脚本中不少是绑定旧控制目录的一次性运维记录，不可盲目重跑。

### 冷恢复空转：目录级差集发现与单生产者汇流

c3559 启动后暴露出恢复策略缺陷：从源根目录重新扫描，在约 77 分钟内检查了约 2,434 万项，99.97% 的目标已经存在，新复制仅 2.1 GiB，22 个 worker 存活但空队列。历史索引同时先串行枚举数百万回执，再进入并行读取；因此不能把进程启动或“索引在恢复”当作数据搬运已恢复。旧清单尾部抽样确有缺失，但反向读取实际只补出了约 4,160 个文件，随后仍大量命中已有目标：清单顺序不是任务完成顺序，反向重放也不能代替缺失工作发现。

`migration_missing_discovery.py` 将数据发现分散到允许的十一节点，每节点 16 个只读目录线程，启动时生成 57,967 个互不重叠的目录扫描分区。目录内先读目标文件名集合，再流式枚举源文件名；已存在的叶子不逐个打开父目录或执行目标 stat，缺失名称才写入每节点独立的候选文件。源目录和目标目录使用不跟随符号链接的打开方式；缺失目标目录只产生候选，绝不由发现器创建数据目录或写目标文件。优先级 1、2 继续排除在 warm 发现范围之外。

名称差集只是候选提示，不是内容相同或复制完成的证明。候选统一流入 `frontier-input/HOST/ready`，`migration_frontier_resume.py` 的唯一生产主线程负责路径预约、任务编号和 SQLite；原有只读预检服务刷新源身份，原有 worker 保持 SHA、源变化检查、冲突拒绝、fsync 和安全发布。所有发现器均无权直接发布复制任务。发现期间的源目录变化、已存在但内容冲突的文件以及硬链接和目录元数据仍由后续完整扫描和正式轮次处理，不能将名称命中计作正式核验成功。

初版汇流在每个至多 512 项的候选文件后等待全部预检完成，实际在途峰值只有 512。改为 16 路候选 JSON 读取，主线程持续填充原有 4,096 项有界流水线，16 个批次客户端使用仍限定每端点 64 路的预检服务；多份候选合并为正常的 64 文件任务，避免小目录产生一文件一任务。只有对应预检和所有已接受任务发布成功后，才并行将候选文件移动至 `done`，保留审计原文，不删除候选或回执。`frontier-input-tuning.json` 可按 control/run_id 绑定热调每组候选文件数和每节点份额，范围 1–4,096；无效设置保持旧配置并报告错误，不热改数据引擎或任务编号。

生产端采用当前小任务账本交接，而非重读旧集群数百万任务的账本。只有经过完整 PID/starttime/argv 检查的生产端可冻结、终止；已有 broker、22 个复制进程、租约和原索引恢复子进程不动，过期的只读扫描/预检子进程按精确身份退出。交接保留本机 SQLite/WAL、当前任务的路径预约及源清单；编号超过全部已发布及已记录预留值，并额外保留一个明确的安全间隔。预终止失败恢复原生产端，终止后的不确定结果不自动重试启动。各次冻结检查点累计保存此前目标存在性观察，监控的历史写入基线和新进程局部速率继续分开。

### 供给流水线与大文件批次长尾

后续采样发现两个独立问题：候选输入的读取、预检、发布、确认仍有组间空窗；同时任务只限制 64 个文件，已有单批约 160 GiB 的任务，空闲线程无法接走批次尾部。30 秒采样中 producer 主线程仅约 0.15 核，不能据此认定 CPU 不够或继续堆复制线程。共享候选目录枚举前 64 个文件名实测约 1.93 秒，而这些条目的 `is_file` 使用目录类型缓存，仅约 7 微秒；真正需要并行的是跨节点队列的 READDIR，不是再加逐文件 stat。

`migration_frontier_inputs.py` 将读取、预检、发布与确认分离：8 路独立目录枚举、16 路候选 JSON 读取，提前准备下一组；主线程仍独占预检提交、路径预约、SQLite 和任务编号。每组记录全部预检 future，且只有相关预检已收集、选中路径已刷新为任务、任务编号发布屏障全部完成后，才异步将原候选移入 `done`。最多保留四组，至多两组尚未进入确认，确认执行器为两线程；下一组预取排除所有已接受组，避免确认延迟期间重复接受同一候选。后台不访问 SQLite，不另起任务所有者。

新任务同时限制 64 文件和 1 GiB，超过 1 GiB 的单文件单独成批，不拆文件，不重写已经领取或发布的旧任务。共享发布池热调为 16 路、最多 64 个在途发布。已有分布式缺失候选时优先消费这些输入，只有候选队列排空后才恢复旧清单反向兜底，避免预取空窗被重复检查已有目标占满。完整源扫描、冲突处理、硬链接和最终正式核验仍保留。

交接前在旧 producer 继续运行时准备当前任务路径集合的本机 primitive 缓存和完整账本，冻结后只合并增量；缓存绑定 control/run_id、文件权限、SHA 和账本前缀，禁止 pickle 全局对象。利用原发布池热调的 drain 边界观察 `pending=0` 后再进行精确身份冻结；不满足条件即保留原 producer，不强行终止。缓存不是跨集群恢复权威，丢失时必须走完整账本路径，不能假装为空集合。

2026-10-23 19:25 的交接保留 114,478 个原任务和全部 22 个 worker 的 PID/启动时刻/argv；broker 与索引恢复子进程未重启，原运行目录 39 个源码摘要与新 bundle 7 个摘要均核对通过。上线后抽查 20,583 个新领取任务，未发现超过批次限制的多文件任务；旧编号范围的 114,478 条 SQLite claim 与交接账本完全一致，旧 pending 已排空。验收记录位于当前运行 bundle 的 `verification.json`。这证明本次交接和批次策略已生效，不代表持续达到 10 GB/s；需继续以相同文件粒度的有效窗口衡量收益，并区分实际写入与已完成文件字节。

### 读与确认隔离，以及尚未解除的确认背压

后续内核等待采样连续观察到原 16 个共享候选 I/O 线程中有 12–15 个停在 `do_renameat2`；候选确认与下一组 JSON 读取共用一个执行器。`migration_frontier_inputs.py` 因此保留独立的 16 路读取池，确认改成每节点一条串行 lane、跨节点并行。生产侧仍只有两个确认组执行器，发布屏障和候选排他预约不变。实际后台预取耗时增加了独立字段 `prefetch_io`，不能把包含主线程等待时间的 `last_prefetch_seconds` 当作纯磁盘读取耗时。

2026-10-23 19:42 的生产端交接约 7.8 秒，保留 159,386 个原任务。上线后实际预取约 2.3–4.7 秒，重命名等待线程降至 4–7 个；70 秒复制窗口约 2.80 GiB/s，传输写入约 2.45 GiB/s，活跃线程区间 209–541。没有重启 worker、broker 或原索引恢复进程。但预检处理率仍约 3,800 项/秒，读写隔离并未消除所有供给限制。

预检 HTTP 请求的实际批次平均仅 23–30 项：旧 `_offer` 在每个候选文件结尾刷新尾批，细碎目录因此造成大量小请求。输入现在在同一发布屏障组内合并为 64 项再提交，客户端进程从 16 增至 32，服务端仍严格限制为十一节点各 64 路元数据操作，生产端在途上限仍是 4,096。`metadata_batching` 单独计量本 producer 的批次数、条目数、满批次数、批次耗时与子进程 CPU，不能把客户端配置数当作服务端实际活跃数。

此时仍不能宣称达到 10 GB/s：96.7 秒窗口完成约 2.39 GiB/s、传输写入约 1.85 GiB/s，文件粒度不同，不能用它与不同时间的短窗口断言并发扩容的因果增益。主循环仍会出现“预取已 ready、预检在途为零、发布积压为零，但三个确认组未完成”的状态，线程活跃最低可降到个位数。确认目前逐文件移动共享盘上的候选原文；每节点确认统计约每文件 0.2 秒，已经形成独立的供给背压。

### 按组持久确认与可核对的任务支撑

`migration_input_receipts.py` 将一组候选的确认写成一份独立记录，原文件保留在 `ready`，不删除、改写或逐个移动。确认只在该组全部预检收集完成、选中项形成任务、相关发布全部成功后发生。记录绑定 control/run_id、生产代际的初始任务编号集合、该代连续分配区间的发布屏障及候选引用，且带内容摘要。先完整写入并 fsync 私有临时文件，再用不覆盖已有文件的硬链接发布，最后同步父目录；未完成的临时文件不是有效确认。

恢复时的任务编号集合来自当前 pending/SQLite claims 的完整冻结快照，primitive 缓存版本 2 同时保存路径和任务编号。旧记录的初始编号集合必须仍被包含，屏障区间中的每个编号也必须存在，不能只比较最大编号。缺失支撑的组不作为已处理候选，原文仍可重新供给；记录不是数据复制完成、目标缺失或内容一致的证据。重复的有效组按候选文件去重，不叠加进度；身份、摘要、路径或结构错误显式报错。

生产交接额外等待所有主进程线程真正停止，而非仅看组 leader 的 `T` 状态，以免后台元数据系统调用在快照之后才完成。冻结后重新枚举 pending，并核对它与 durable claims 的完整编号并集必须与账本完全一致；缺项或多项均恢复原 producer，不强行终止。新的 producer 不继承前任的 `health_verified` 标志，必须完成自身运行验收。

候选读取改用每节点一个持续目录游标，额外预读但受全局上限截断的引用会保留在有界缓冲中，不会丢失。游标结束后重新检查变化，遍历错误不能当作空队列。原文保留也意味着不能在每个旧清单小批次前从头枚举全部已确认文件；后续保护以目录版本及有界轮询减少重复扫描，并定期强制完整遍历，目录时间不作为正式完整扫描的证明。

### 发布主线程的重复路径检查

确认背压解除后，主线程仍在 `BoundedTaskPublisher.submit` 同步执行 `_fresh_target`，发布线程随后再做同样的检查。当前共享 pending 路径的只读测量平均每批约 8.8 ms，主线程 10 秒采样约 82% 时间停在元数据 RPC，CPU 仅约 0.07 核。这是具体的串行元数据往返，不能归因为算力不足，也不能据此声称全部 RPC 时间都属于这一个调用。

新增 `check_on_submit=False` 仅供当前单一编号所有者选择：主线程保留重复编号/路径的内存拒绝、深拷贝和有界容量，文件系统防覆盖检查仍由发布线程在写入前执行。已存在文件、快照路径或符号链接仍拒绝；错误通过 `PublicationError` 回传，失败不计成功，也不能触发候选确认。经典调用默认保持同步检查；发布池热调重新创建时保留所选策略。此项是否提速必须以实际部署后的相近文件粒度窗口验证，而不是将 8.8 ms 微测量直接换算成端到端增益。

### 小文件批次热调与缩短接管尾部

后续版本在 `frontier-input-tuning.json` 增加可选的 `copy_batch_files`，严格允许整数 64、128、256、512。它与 control/run_id 绑定，由生产主线程应用，只影响随后生成的 warm 恢复任务；已发布任务、租约、文件内容与编号不改写。多文件任务仍最多 1 GiB，超大单文件独立成批。状态记录 revision、开始生效的任务编号及最近八次策略变更；无效配置保留旧策略，错误可见。warm 供给结束后恢复原有正式扫描批次配置，不修改 config.json 或正式轮次语义。

先通过真实 256/512 文件复制、逐文件 SHA、现有 sharded broker 的 claim/done 和重复回执测试，确认复制循环没有 64 项协议限制，回执仍小于 64 MiB 请求上限；该版本全量 868 项测试通过。这不是取消逐文件安全检查，也不是把调大批次等同于提高磁盘吞吐。批次更大可能增加领取粒度与完成尾延迟，必须保留在线下调能力。

交接准备增加两次有界的在线账本追赶，旧 producer 此时继续供给；冻结后仍完整核对 pending 与 claims，而非只看最大编号。原 producer 退出且释放协调锁之后、启动后继之前，发布一次内容不变、带 `loading_successor` 标记的状态心跳，避免不必要的缓存过期；后继完成接管后移除标记。不能由第二个后台线程伪造 producer 心跳，也不能忽略真正过期的状态。

### 目录属性真正并行，以及源端派发热调

随后发现扫描进入另一种区域：预检在途降到个位，源扫描仍在前进。每个 source reader 原来只把选中的文件 stat 放进线程池；目录的 is_dir/stat/open/fstat 仍在单个循环中串行。因而“32 个进程、每进程 8 线程”不等于目录发现拥有 256 条独立属性路径。新实现把一页至多 1,024 个子项的分类和目录属性放入原有的 8 线程有界池，之后仍按原页序回收；文件全属性仍经父进程的路径选择，清单、硬链接 canonical、任务编号和 SQLite 仍只有父进程一个拥有者。所有子目录句柄在返回前关闭，原来的 inode 复核、符号链接拒绝、取消和有界本地 DFS 保留。续扫遇到已经记录的目录失败时也必须记录错误，不能被 seeded path 去重吞掉。

第一组同目录重复测试出现 1.15 s 到 0.005 s 的差值，明显有缓存预热，未用作提速证据。改为互不重叠的 512 个真实源目录、交错 1/8 线程，每组 64 目录：串行为 49.7–64.5 ms，8 路为 8.6–10.2 ms，全部返回目录且无错误。这证明该元数据段具备并行空间，不直接保证端到端扫描有同等倍数。

### 预检反压：批内复用父目录，而非继续堆源读取进程

原来虽然 HTTP 按最多 64 文件打包，每个文件仍重复执行安全父目录打开和 leaf stat。新入口 `migration_probe_batch_parent.py` 只把父目录打开限定到批内每个不同父目录一次。每个工作项持有自己的 dup FD，原有逐文件 no-follow stat、源变化刷新、认证、STOP、信号量、结果顺序和可选小文件策略均保留；源目录不使用该目标缓存。每个请求最多 64 个父目录，互不相同的父目录打开不持有共同 I/O 锁。没有跨批缓存、目录名猜测、仅凭历史记录宣告存在或跳过内容校验。

### P4 小文件阶段：回执路径也会限制有效复制并行度

随后整体近五分钟搬运一度降至约 0.85 GB/s。P4 当时有 1,227 个活跃项，其中约 505 个标记 awaiting_receipt；生产端处于 4,096 任务队列背压，不是缺少可搬数据。broker 约 1,100 个请求线程，五次采样中 5,119 次 futex 等待、253 次目录写锁等待，另有少量 RPC 等待。其运行标记仍集中于一个 running 目录，重复父目录 mkdir 以及先排空一个 pending 分片，也会把 64 路文件系统并发聚集到相同目录锁。增加复制线程不能消除这个控制路径。

`migration_priority4_broker_sharded.py` 复用既有 P4 租约/回执实现，仅对新 claim 使用 64 个 running 子目录、按分片轮转候选、最多 8 路目录枚举，并对已准备的 running/done 父目录省去重复 mkdir。旧 claim 的原运行路径、owner、lease、payload 和 SQLite 不改；已完成回执、丢失回复、旧 flat 租约及同 owner 并发请求均有测试。正在运行的 P4 producer 已只读核实支持混合 flat/sharded 的 queued_count，不能让分片后被误判成空队列。生产端、worker、端口和线程数都不应因该版本改变；实际 broker 交接需要另行批准，不能将离线测试通过冒充线上部署。

同阶段单个 master 的 NFS 增量采样显示 WRITE 约 0.672 GB/s、客户端平均排队约 1,425 ms、RPC 往返约 6.2 ms；GETATTR 排队约 18.7 ms、往返约 2.5 ms。这是具体的客户端/控制路径等待证据，不是“磁盘慢”的泛称，也不能据一个节点或累计历史计数推断十二节点物理盘吞吐。现有 TCP RPC 槽位上限已经为 65,536；没有证据支持盲目增大，也没有在复制中重挂载或改全局内核参数。文件大小与数据/元数据比例变化会改变 GB/s，不能用早先大文件阶段的 10 GB/s 直接替代当前小文件阶段的容量判断。

### P4 供给再次落后：线程不是独立 CPU，且任务控制成本按批收取

后续五分钟完成/逻辑传输降至约 0.67 GB/s，P4 生产端不再处于任务队列反压，32 个发布线程也没有占满。约 21 秒采样发布约 41 批/s，抽样批次平均约 15.45 MB，二者乘积约 0.63 GB/s，与端到端速率接近。97 线程的生产端合计约一核，其中主线程约 0.20、64 个源线程约 0.75、发布线程约 0.13 核。目录队列满时使用本地 DFS，实际持有约 800 个目录 FD，不能把“待派发目录数少”误解为没有可并行的目录。此时 broker 已完成前述分片更新；没有证据把全部等待继续归因于回执热点、磁盘或缺少 GC 热调入口。

有界 CPU affinity 对照未取得可归因的吞吐收益，均已恢复：一个空闲 P3 复制进程由 192 CPU 的许可范围临时缩至 4 CPU，CPU 消耗降低，但恢复后的 P4 吞吐反而继续增加；生产端的相同对照使任务供给下降。因此不推广 affinity，也没有调整复制线程数、全局内核参数或停止空闲的复制进程。这些试验控制器有独立恢复 watchdog，不能把实验中短时文件组合变化当作优化收益。

另一个可复现成本在复制端 HTTP 客户端构建。实际 Python 3.12 标准库的 `build_opener(ProxyHandler({}))` 默认仍创建 HTTPS handler/SSL context；现有 worker 每次 HTTP 领取和回执均重建一次。主节点不发网络请求的隔离复现中，构造 32 次的 CPU 消耗约为：1 线程 1.28 s、4 线程 4.76 s、8 线程 8.07 s；第二组分别为 1.44/3.73/7.10 s。这证明并发构造本身有成本，不是对现有进程的完整栈归因，更不能单据该样本计算集群可恢复的 GB/s。

候选 `migration_priority4_fast_run.py` 仅替换已另行授权的 P4 生产端。使用 16 个预置 spawn 目录读者、初始派发 8 路、每进程 8 个属性线程；路径集合、清单、硬链接 canonical 和编号仍只有父进程拥有。显式 P4 排除项必须精确为顶层 `eai_pwm`；原 P1–3 默认行为不变。目录路径使用已有严格 no-symlink 的 openat2/逐级回退实现，目录分类属性进入有界线程池。配置在后台做 fail-closed 刷新，STOP 仍直接检查；发布只省去主线程的重复目标检查，写线程仍核验不存在的任务路径。已经验证并准备的 archive/pending 父目录不再重复 mkdir。首轮索引为空时只查一次空表，非空索引仍逐文件带回原 known 证明。

新小文件任务上限为 256 文件/256 MiB，减少每文件分摊的 HTTP、租约和回执操作，逐文件 SHA/身份检查完全不变。每 128 批检查未完成任务，达到 2,048 批时反压；该上限仍可容纳 1,536 个复制线程，不通过无限堆积任务获得表面吞吐。P4 scope/run/control 绑定的 `SourceLimit` 仅改变新目录派发预算，不停止在途读者；原 P3 调参 scope 默认值不变。

### P4 同轮接续必须先证明扫描前沿和已接受发布

普通重启会重新读取几十万份共享盘任务并重扫已经完成的目录。为避免在供给交接时支付这笔成本，`prepare_priority4_source.py` 与 `prepare_priority4_assignments.py` 在旧生产端继续供给时旁路预载。准备记录本身明确不授权接管。

原冻结线程扫描器的事件队列是单消费者、有界 FIFO。只读 FD 观察不能单独证明目录已完成；准备器先保留活动 frame、尚无子记录的目录和错误目录及所有祖先，再利用原 4,096 批反压与轮询余量，证明一次捕获之后的 manifest flush；跟进完整清单记录超过 8,192 个队列容量后，才获得保守候选集合。后续新目录/错误仍剔除其祖先候选。不能使用 `qsize()`/`empty()` 作为退出或刷出证明，参见 [Python 3.12 Queue 语义](https://docs.python.org/3.12/library/queue.html)。

该准备器得到的约 2,511 万条记录、约 257 万候选目录仍不是最终交接凭证。接续入口必须校验原清单 inode、前缀 SHA、私有 primitive-only 缓存的权限/所有者/SHA、原 producer PID/start tick/完整 argv 和冻结源码；旧端正常 SIGINT 退出后，才可合并末尾、要求完整记录结束、接管同一 coordinator flock，并按 dev/ino/mtime/ctime 复核候选目录。下一正式轮次默认做完整新扫描，不采用本轮 metadata shortcut。

任务预载从同一 broker 的只读事务提取连续 payload 前缀，逐任务/逐路径验证范围、编号、条目计数、唯一分配及普通文件 canonical。JSON1 路径提取避免把数千万份完整属性字典全部构造成 Python 对象；原 broker payload 与共享 archive 仍是持久权威。一次早期验证错误地把 `nlink=2` 的符号链接也纳入普通文件 canonical，准备器因此在任务 344362 附近拒绝；对照任务 73034 证实是同一符号链接 inode 的两个合法路径，不是复制损坏。没有因准备失败切换生产端；修正后的缓存和最终 delta 均只对普通文件建 canonical，增加回归用例，旧不可变 bundle 保留。

交接控制器要求新入口预载并追平，十二节点全部 48 个复制进程的新鲜原生身份核验，以及两个 broker/P3 producer/metrics 和源码摘要保持不变。只向精确的原 P4 producer 发送一次 SIGINT，不向复制进程、broker、训练或节点发信号；不自动升级 SIGKILL，不盲目重试已发起事务。旧端退出后校验完整 archive 编号集合、broker 连续前缀和少量最终 archive/pending delta，保留所有旧 lease；未派发尾批必须同时满足路径成员关系和完整 copy_entries 差值，不能只猜最后 64 个文件。随后才追加原 manifest、从原下一编号继续。角色记录显式指向后继并保留 predecessor；原节点计数和监控历史不清零。

候选的上线状态与稳态收益须以独立运行 bundle 的 `native-tests.log`、`standby.json`、`handover.json`、`release.json` 和后续原生身份/速率采样为准。离线全量测试以及私有目录上真实线程 FIFO → 进程读者接续测试通过，不能单独证明已经上线或达到 10 GB/s。实际第一轮交接记录如下。

### P4 路径候选只准备不激活，并强制继承真实历史计数

`migration_priority4_path_worker.py` 是一个新的、尚未部署的入口，不在线改写旧入口。策略固定为 `native_readonly`，只接受 worker-10 的 64 线程 supplement、原 30 秒状态缓存和同一独立 P4 control；没有同时启用 O_PATH、HTTP 客户端替换或数据引擎改写。启动时绑定原 P4 完整静态源码清单及其 SHA，要求所有原模块在新 bundle 中逐字节相同，并校验实际导入的模块确实来自新冻结目录。

### 空闲轮询 CPU 修复：复用线程私有 opener，而非减少任务领取频率

用户选择保持原配置、不延长限核试验后，全部 CPU 许可范围保持原值；新的请求是直接修复空闲轮询开销。原 primary 和 supplement 在每次 `/claim` 和 `/done` 请求中调用 `build_opener(ProxyHandler({}))`。运行侧 Python 3.12 会为默认 HTTPS handler 初始化验证证书的 SSL context，即使实际 broker 为内网 HTTP，也重复支付此成本。此前现场 CA 文件描述符和构造实验支持这一方向；不能据此把全部在线 CPU 或查漏延迟归为这一个原因。

`migration_run.BrokerClient` 将 opener 放在线程私有存储中，每个客户端的每个工作线程只成功构建一次。两个 worker 入口共同使用该实现。urllib 内部的可变请求状态不跨线程或跨客户端共享；每个请求仍新建 Request、真实请求 broker、解析并关闭响应，认证、JSON、30 秒超时、响应校验不变。继续使用空 ProxyHandler 绕过环境代理，同时保留默认 HTTPS 证书和 hostname 验证。这里只复用 handlers，不声称已经实现 TCP 长连接。
