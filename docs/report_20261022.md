## 时间主要花在哪里：难点与解决的问题

本次迁移同时承担海量目录发现、在线源变化处理、多节点唯一分配、跨重启恢复、内容验证和低优先级运行约束。复制节点能够跑起来，只解决了数据搬运链路的一部分；实际推进速度还取决于扫描、检查、发布是否能持续向复制节点供给。现有证据不能把所有停顿精确归因到各环节小时数，以下区分可量化记录和机制判断，不给未经测量的耗时分摊。

### 1. 数千万条历史记录恢复，不能靠重新启动立即续上

历史成功证据分散在多个控制目录及大量小回执中。恢复需要沿祖先链读取、去重、校验所有权与源/目标身份，既不能丢掉此前工作，也不能把不完整文件误当作成功。在共享存储上，这是一项元数据密集工作。

原恢复流程还将约 **540 万个旧候选**逐项重新提交 HTTP 存在性检查，记录中的速度约 **700 项/秒**，理论处理时间约 **2.14 小时**。这个量级说明，只估算 JSON 解析耗时会严重低估恢复供给空窗；它不是已测定的全部停顿时长。

对应改进是：历史索引并行恢复；旧候选完整落入本地 spool；新扫描与历史候选交错供给；大文件候选优先；进程仍在线时预先构建带摘要、身份和边界的恢复 checkpoint，交接时只处理短尾增量。当前部署状态已显示 `interleaved-large-first`，并出现持续任务发布和新增复制，说明新链路已在工作；长期吞吐收益仍需持续窗口验证。

### 2. 共享存储的小文件与元数据长尾，使高线程数无法直接转化为吞吐

源和目标分别通过共享文件系统访问。海量目录遍历、源 `stat`、目标存在性检查、回执和状态文件读写都可能受延迟影响。早前代码归档记录过目标 probe 错误率约 **79.8%**、活跃复制线程仅 **103/1536** 的诊断样本，不能据此认定当前仍有相同错误率，也不能把错误全部解释为数据损坏。

已实现并部署分布式只读目标检查，将检查分散到 12 节点，并限制单端点并发及总在途数；网络或协议失败保留重试和本地回退，不把检查失败当成“已存在”。扫描对已种入清单的非目录条目减少重复元数据操作，同时继续遍历目录，避免漏掉新子项。

文件粒度也会显著改变同一字节吞吐所需的操作数。设计归档中一次前后各 300 批抽样，平均文件大小从约 233 MiB 降至 1.7 MiB；相同字节吞吐需要约 137 倍的文件处理率。该样本用于说明元数据与派发压力，不能据此认定本次全部文件都发生了相同比例变化。源目录遍历仍由 master 的单一进程和 128 个目录线程完成；12 节点分担复制与目标检查，并不是 12 节点同时遍历源目录。

### 3. 生产端串行发布与控制面访问会让复制端断粮

此前即使 producer 有大量线程，主线程同步发布任务文件仍会被共享盘延迟阻塞。**16:58 的观测中，12 节点心跳正常、1536 线程全部空闲，保留的约 15 分钟样本新增复制为零；当时 producer 在历史清单重放且此次交接后发布数为零。** 这是任务供给空窗的直接证据，不能用目标 SHA 校验成本解释。

任务发布现在使用有界并行池：8 路后台发布、最多 64 批在途；主线程仍独占路径预约、任务编号、SQLite 索引及计数。这样减少共享盘发布串行等待，同时保留单一生产者和唯一任务分配，不通过启动多个相互不知情的生产者冒险提速。broker 也将慢文件系统操作与短数据库事务分离。

当前交错供给实现还合并了重复 STOP 轮询，并记录 GC、供给计数，便于继续区分控制面开销与实际数据读写。归档中的 SQLite 点查样本约 0.007 ms，只说明不能凭实现结构就把 SQLite 认定为主要瓶颈。

### 4. 运行环境限制与训练保护触发，会产生额外恢复周期

并行扫描需要大量同时打开的目录和连接。历史生产进程曾因 SSH 启动继承 **1024 的文件句柄软上限**而遇到 `EMFILE / Too many open files`。现在生产入口在产生协调器副作用前自行提升并检查至少 **65,536**，不依赖 shell 继承；当前状态报告 `[65536, 1048576]`。对应回归用例从真实低限额子进程启动并同时打开 1536 个描述符，验证能够越过旧阈值。

原训练 watchdog 会在基线训练 launcher 退出或重启时触发复制 STOP。当前配置已明确 `training_watchdog_enabled=false`，代码支持按配置退出该耦合监控，并提供独立恢复复制节点的入口；这不改变数据校验，也不意味着可以忽略其他来源的 STOP。此前已中断文件缺少完整成功证明时仍需重新复制。训练退出的时间和具体损耗没有完整分项统计，因此不在本报告中虚构停顿小时数。

### 5. 状态缓存过期使领任务反复重试，需要保留安全语义地调整

共享盘状态读长尾会耗尽原来 3 秒的新鲜度窗口。归档中一次约 61 秒采样，12 个进程累计新增 **1666 次**相关重试。滚动更新工具将目标有效期设为 30 秒，每次只处理经过租约归零、心跳和无数据 FD 检查的空闲进程；其他节点及在途复制继续运行。刷新失败或超过有效期仍停止领新任务，STOP 仍保留检查。

这项改进解决状态抖动导致的控制面重试，不替代任务供给优化。代码中有集群滚动、传播等待和结果不明时停止推进的保护；不能仅凭脚本存在认定每个运行进程都已使用同一版本，仍应逐进程核实部署记录和实际参数。

### 6. 完整性校验、在线变化与元数据保留本身有成本

复制引擎不是直接执行 `cp`，而是每块最多 8 MiB 的 `read/write`：读取源时计算 SHA-256，写目标临时文件，再读目标校验，检查源身份未变化，保留元数据并 `fsync` 后发布。普通非稀疏新文件每 1 TB 逻辑数据约产生 3 TB 应用层读写处理；校验可能命中缓存，不能当作同量物理盘流量。

临时文件发布防止未完成文件暴露为正式副本；源在线变化需要后续轮次；硬链接、稀疏文件、权限/xattr 和目标冲突都有独立处理。这些机制使迁移可恢复、可审计，但校验和元数据成本只能解释复制工作期间的一部分耗时，不能掩盖线程空闲造成的供给损失。

## 后续推进与验收点

1. 维持单一 producer，持续观察发布速率、pending、在途及完成速度，优先避免再次长时间断粮；不以提高配置线程数代替解决供给问题。
2. 每小时更新新增完成 TB 和过去 6/12/18 小时有效速度。若持续回落到约 1.34 GB/s，应调整 1 PB 日期，并定位供给、存储读写、校验各段的证据。
3. 形成当前与历史索引的按范围、路径、版本去重结果，分别报告“实际新复制量”和“当前唯一成功副本量”。
4. 完成优先级 1–3 的轮次、元数据和问题审阅，满足独立交接条件后推进第四范围；第四范围完整清单形成后重算全任务验收 ETA。
5. 核对全部队列、后台进程、最终 summary/finalize、源变化项、冲突与错误；不把存在性预检或累计字节计数当成最终验收。
